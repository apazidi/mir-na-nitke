# Codex launchbook — Мир на ниточке 1.0

> **Текущая модель (с 5 ноября):** этот документ описывает первоначальный эксперимент с двумя Codex-сессиями. Для дальнейшего развития **первых 5–10 полянок через одного Product Director** использовать [game-product-director](../.agents/skills/game-product-director/SKILL.md) и [PRODUCT-VISION-5-10-SCENES.md](PRODUCT-VISION-5-10-SCENES.md). Не нужно запускать много отдельных чатов и вручную пересылать результаты.

**Версия:** 2026-11-05. **Цель:** перейти от одного ChatGPT-чата к отдельным Codex-сессиям, не теряя общего контекста и не создавая конфликтов в GitHub.

## 0. Реальный статус

- Этот чат служит для постановки задач, архитектурных решений и приёмки PR.
- Codex-сессии не созданы этим документом и не запускаются автоматически: их открывает владелец проекта в Codex.
- В репозитории уже есть `AGENTS.md`, skills `create-knit-item`, `create-meadow`, контракты, QA и автообнаружение ready-пакетов.
- Игровой продукт 1.0 ещё не опубликован и пока не реализован. Исторические версии не изменять.
- Работа ведётся по уже созданным GitHub issues [#8](https://github.com/apazidi/mir-na-nitke/issues/8), [#9](https://github.com/apazidi/mir-na-nitke/issues/9), [#10](https://github.com/apazidi/mir-na-nitke/issues/10), [#11](https://github.com/apazidi/mir-na-nitke/issues/11), [#12](https://github.com/apazidi/mir-na-nitke/issues/12), [#13](https://github.com/apazidi/mir-na-nitke/issues/13).

## 1. Как запускать

**Первая волна — ровно ДВЕ независимые сессии, а не четыре:**

| Сессия | Issue | Зона владения | Что НЕ делает |
| --- | --- | --- | --- |
| Engine | #8 | `product/app/core/**` + модульные тесты core | Не меняет UI, общий дизайн, предметы |
| Art | #11 | `product/art-experiments/rabbit-v1/**` + собственные review-материалы | Не меняет движок, CSS, исторические игры |

Агент в каждой сессии должен завести **свою feature-ветку**, выполнять проверки, открыть PR и не сливать его самостоятельно без приёмки. Отдельный workspace / git worktree для параллельной работы: не заставлять две сессии коммитить из одного рабочего дерева.

**Вторая волна — ПОСЛЕ фиксации базового интерфейса движка, а не после полного завершения всей игры:**

- #10 Content Runtime: чтение сгенерированного каталога в браузере, layout-independent stage/slot API. Может параллелиться с UI, когда контракт engine read-model согласован.
- #9 GameShell: реальный UI мастерской/полянки по существующему design contract и арт-эталону; получает event API из engine.
- #13 Build & Publish: сборка новой версии только на отдельный /play/ preview, старые опубликованные прототипы не менять.
- #3 Resource Loop: сквозной цикл bunny → meadow → yarn → flower после склейки engine + shell.

**Третья волна — после первого vertical slice:** #12 доводим навыки производства новых items/meadows и проверяем два настоящих параллельных агента контента. Не плодить множество узких skills до проверки первых реальных исполнений.

## 2. Готовый запрос для Codex — сессия Engine

Открыть отдельную Codex-сессию с репозиторием `apazidi/mir-na-nitke` и отправить:

> Реализуй GitHub issue #8 «Engine core» для новой игры 1.0. Сначала прочитай AGENTS.md, product/ROADMAP-1.0.md, product/architecture/CONTENT-CONTRACT.md и RESOURCE-LOOP.md. Создай ветку `feat/engine-core-1`. Работай только в product/app/core/** и своих unit tests, не меняй design-system, контент, старые PoC и shared UI. Движок должен быть детерминированным, без DOM и localStorage в core: отдельные yarn и work, idle/offline, click, покупка улучшений, старт проекта и завершение, события петтинга с лимитами, serializable save model. Сначала добавь минимальные типизированные/тестируемые API и зафиксируй интерфейс для UI в описании PR. Пройди npm --prefix product test и validate, исправь ошибки. Открой PR в main со сводкой, тестами, ограничениями, но не сливай самостоятельно. Не выдавай временную dev-сборку за готовую игру.

**Критерий первого результата:** engine tests + документированный минимальный API событий/read-model. UI пока не запускаем, чтобы не угадать интерфейс.

## 3. Готовый запрос для Codex — сессия Art

Открыть **другую** Codex-сессию/отдельный рабочий каталог с тем же репозиторием:

> Возьми issue #11 «Art pipeline 1.0». Прочитай AGENTS.md, design-system/DESIGN-CONTRACT.md, design-system/reference-v4.webp, product/architecture/UI-ASSET-POLICY.md и skill .agents/skills/create-crochet-art/SKILL.md. Создай ветку `art/rabbit-golden-v1`. Первый результат — НЕ 8 независимых генераций кролика, а один воспроизводимый художественный master, один golden frame (кролик/стол в утверждённом стиле) и 3–4 согласованных стадии из одного master, плюс contact sheet и скриншоты на 390×844. Не меняй engine, глобальный UI, чужие content packages и существующие опубликованные прототипы. Складывай работу в product/art-experiments/rabbit-v1/**. При отсутствии image generation/rendering опиши доступный арт-пайплайн и честно отметь blocker; не имитируй производство качественной графики примитивами CSS. Открой PR для художественной приёмки, **не сливай** до визуального одобрения.

**Критерий первого результата:** согласованная сцена, проверенная по референсу. Даже отличная документация без игровых изображений не закрывает #11.

## 4. Что отправлять в этот ChatGPT-чат после работы Codex

Достаточно ссылки на PR. Здесь проверяем требования, diff, CI, визуальную приёмку, конфликты, затем решаем вопрос о merge. Если нужны доработки, возвращаем конкретные review comments той же Codex-сессии.

Один PR — одна ответственность. Не нужно копировать сюда всю историю Codex: код, тесты, макеты и комментарии должны оставаться в GitHub.

## 5. Минимальный integration API boundary

Не замораживаем заранее весь engine. Для начала engine PR должен предложить и протестировать:

- `createInitialState(config)` — чистая модель игры с версиями данных;
- `advanceTime(state, now, config)` — начисление offline/idle один раз;
- `dispatch(state, action, config)` — click, startProject, buyUpgrade, placeItem, pet;
- `selectView(state, catalog)` — read-model: текущий проект, прогресс, кошелёк, доступные действия, слоты полянки.

Это имена-кандидаты, не уже существующий контракт. До начала #9/#10 согласовать интерфейс по PR #8; не создавать параллельно собственные несовместимые game stores.

## 6. Контроль качества и ограничения

- Не «дописывать» игру старым v3-stage или v4.1 HTML; новая реализация живёт в `product/`.
- Draft-пакеты без готового арта не показывать игроку.
- У каждого PR отдельная ветка, тесты и зона изменений; чужие файлы не менять.
- Визуальный CI обеспечивает регрессию старого UI, но не гарантирует соответствие новому эталону: human review обязателен.
- Не закрывать задачу только потому, что manifest/CI зелёные. Изделие должно быть действительно играбельным и красивым на телефоне.
- Опубликованный /play/ — цель integration gate, не результат этой инструкции.

## 7. Когда подключать третью и четвёртую сессию

**После PR с минимальным интерфейсом #8** можно создать Codex-сессии для #9 (UI) и #10 (runtime integration); выделить отдельные файлы/ветки. Нет необходимости ждать окончания художественного конвейера, чтобы писать каркас UI, но нельзя утверждать его визуальную готовность без настоящего арта.

**После первого общего экрана** с реальным кроликом закрыть #3 и #13, а затем пилотировать #12 как «контентную фабрику» на новых изделиях.

**Идея:** две параллельные задачи сейчас, две после первого контракта, много независимых item/meadow-агентов только после появления работающего движка.
